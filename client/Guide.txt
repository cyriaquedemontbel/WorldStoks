Partie 1 : Guide pour la Création du Backend et de la Base de Données
Le principe fondamental est le suivant : la base de données devient la source unique de vérité. Le frontend n'est plus qu'une interface pour visualiser et demander des modifications à ces données. Toute la logique métier (calculs de prix, vérification des fonds, etc.) est déplacée vers le backend.

A. Structure de la Base de Données (Schéma)
Vous aurez besoin de plusieurs tables pour modéliser votre application. Voici un schéma de base (utilisable avec SQL comme PostgreSQL ou MySQL, ou adaptable pour NoSQL comme MongoDB) :
Table Users
id (Clé Primaire, ex: UUID)
email (Texte, Unique)
password_hash (Texte) - TRÈS IMPORTANT : Ne stockez jamais les mots de passe en clair. Utilisez un algorithme de hachage comme bcrypt.
cash (Numérique, ex: DECIMAL(15, 2)) - Le solde de l'utilisateur.
is_admin (Booléen)
Table Stocks
ticker (Texte, Clé Primaire, ex: 'PSG')
name (Texte)
price (Numérique, ex: DECIMAL(15, 2))
description (Texte)
max_supply (Entier Grand)
circulating_supply (Entier Grand)
change_24h (Numérique)
change_percent_24h (Numérique)
volume_today (Entier Grand)
turnover_today (Entier Très Grand)
Table Portfolios (ou Holdings)
user_id (Clé Étrangère vers Users.id)
stock_ticker (Clé Étrangère vers Stocks.ticker)
quantity (Entier)
Clé primaire composite sur (user_id, stock_ticker)
Table Transactions
id (Clé Primaire, ex: UUID)
user_id (Clé Étrangère vers Users.id)
stock_ticker (Clé Étrangère vers Stocks.ticker)
type (Enum: 'buy' ou 'sell')
quantity (Entier)
price_per_share (Numérique) - Le prix au moment de la transaction.
timestamp (Timestamp)
Table StockHistory
id (Clé Primaire)
stock_ticker (Clé Étrangère vers Stocks.ticker)
price (Numérique)
timestamp (Timestamp) - Pour enregistrer les points du graphique.

B. API Endpoints du Backend (Routes)
Votre backend (créé avec Node.js/Express, Python/Django, etc.) devra exposer une API REST que le frontend pourra appeler.
1. Authentification (/api/auth)
POST /register : Crée un nouvel utilisateur. Hache le mot de passe, l'insère dans la table Users.
POST /login : Vérifie l'email et le mot de passe (en comparant les hachages). Si c'est correct, renvoie un token JWT (JSON Web Token). Le frontend stockera ce token.
GET /me : Route protégée. Le frontend envoie le token JWT. Le backend le valide et renvoie les informations de l'utilisateur connecté (sans le hash du mot de passe).
2. Données des Marchés (/api/stocks)
GET / : Renvoie la liste de toutes les actions de la table Stocks.
GET /:ticker : Renvoie les détails d'une action spécifique, y compris son historique de prix depuis la table StockHistory.
3. Transactions (/api/trade) - Routes protégées
POST /buy : C'est ici que se trouve la logique la plus critique.
Valider le Token JWT pour identifier l'utilisateur.
Recevoir { ticker, quantity } du frontend.
Lancer une transaction de base de données (pour s'assurer que toutes les étapes réussissent ou échouent ensemble).
Vérifier si (stock.price * quantity) <= user.cash.
Vérifier si (stock.circulating_supply + quantity) <= stock.max_supply.
Déduire le coût de user.cash.
Ajouter/mettre à jour la ligne dans la table Portfolios.
Calculer l'impact sur le prix (comme vous le faisiez dans le frontend).
Mettre à jour price, circulating_supply, etc. dans la table Stocks.
Créer une nouvelle entrée dans la table Transactions.
Valider la transaction de base de données.
Renvoyer le nouvel état de l'utilisateur (cash, portefeuille) au frontend.
POST /sell : Logique similaire mais inversée.
4. Données Utilisateur (/api/user) - Routes protégées
GET /portfolio : Renvoie le portefeuille de l'utilisateur en joignant Portfolios et Stocks.
GET /history : Renvoie l'historique des transactions de l'utilisateur depuis la table Transactions.
POST /funds : Gère les dépôts/retraits en mettant à jour user.cash.
5. Gestion Admin (/api/admin) - Routes protégées (admin seulement)
POST /stocks : Crée une nouvelle action.
PUT /stocks/:ticker : Met à jour une action existante.
DELETE /stocks/:ticker : Supprime une action.
6. Intégration IA (/api/market) - Route protégée (admin seulement)
POST /update-ai : SÉCURITÉ ! C'est ce point de terminaison qui appellera l'API Gemini.
Il reçoit la demande du frontend.
Il utilise la clé API Gemini (stockée de manière sécurisée dans les variables d'environnement du backend).
Il appelle Gemini, reçoit la réponse, et met à jour les prix de toutes les actions concernées dans la table Stocks.
7. (Optionnel mais recommandé) Mises à Jour en Temps Réel
Pour que les changements de prix soient visibles par tous les utilisateurs instantanément, utilisez des WebSockets (avec une librairie comme Socket.IO).
Quand une transaction (achat/vente) ou une mise à jour par l'IA modifie un prix, le backend envoie un événement WebSocket à tous les clients connectés avec le nouveau prix de l'action. Le frontend écoute cet événement et met à jour son état local en temps réel.


Partie 2 : Modifications du Code Frontend
J'ai réorganisé votre code pour qu'il communique avec ce backend. La logique a été extraite de App.tsx et placée dans un nouveau fichier api.ts pour plus de clarté.
Principaux changements :
Nouveau fichier api.ts : Centralise tous les appels fetch vers votre backend. Il gère l'ajout du token d'authentification aux requêtes.
App.tsx refactorisé :
Suppression de toutes les données mock (mockUser, initialStockData).
Utilisation de useEffect au chargement pour récupérer les données initiales (actions, utilisateur connecté) depuis le backend.
Les fonctions comme handleLogin, handleBuyStock, handleUpdateMarket appellent maintenant les fonctions correspondantes dans api.ts. Elles ne contiennent plus de logique métier.
L'état est mis à jour en fonction de la réponse du backend.
Gestion de l'authentification : Le token JWT est stocké dans localStorage après la connexion et supprimé à la déconnexion.
